# Impeccable

Pi-native exposure of the [Impeccable](https://github.com/pbakaus/impeccable) design skill — "the design vocabulary for your coding agent." Impeccable gives the model the tools and permission to design, redesign, shape, critique, audit, polish, harden, animate, and otherwise improve frontend interfaces: websites, landing pages, dashboards, product UI, components, native iOS/Android screens, and design-system capture (`DESIGN.md`, tokens).

This extension is a **pinned vendored fork** of the released `skill-v4.8.0` distribution (commit `414603bf14c7a344edb466bb1f85690c77ce8b7d`, engine `0.1.18`, Apache-2.0). See [`LOCAL-PATCHES.md`](LOCAL-PATCHES.md) for the complete, deterministic patch ledger and [`upstream.json`](upstream.json) for provenance.

Every template routes to the installed skill through the `<location>` Pi advertises for the skill and resolves the skill directory as `<skill-base-dir>`; no absolute path or project-relative `.pi/skills` path is baked in. The templates are plain Markdown with native `$ARGUMENTS` expansion — there is no TypeScript command dispatcher.

`impeccable_run` takes an `argv` array (the verb first, its arguments after), plus optional `cwd` and `timeoutMs`. It sets the upstream `IMPECCABLE_PROVIDER_ID=pi` and installed `IMPECCABLE_SKILL_DIR`/`IMPECCABLE_SELF` context, captures bounded stdout/stderr, and reports a structured status: exit 0 is `success`; the `detect` verb's exit 2 is `findings`; any other nonzero exit is `error` with its diagnostics. It resolves the engine from a deliberate `IMPECCABLE_BIN` override, a verified version-pinned cache, or a digest-verified download (`IMPECCABLE_DOWNLOAD_BASE` and `IMPECCABLE_HOME` remain honored); ambient executables are never selected, and unsupported platforms, missing checksums, and download/setup failures are reported as `unavailable`. Timeouts and cancellation kill the child; excess output is reported as truncated and never presented as a complete result.

Existing collection commands are untouched: `/polish` (Writer), `/review`, `/simplify`, `/deslop`, `/verify`, `/commit`, and all extension commands keep their identities. The `design-*` namespace does not collide with them.

## Current task scope (T5)

T1 retained the complete released distribution and native prompts; T2 added the managed engine; T3 added native questions, complete role delegation, and capability guidance. T4 adds project-controlled detector feedback and Pi management operations. T5 adds a lazy session owner for the full native live protocol. Startup registers tools and lifecycle handlers without spawning, downloading, opening dialogs, or writing project files.

`impeccable_question` takes 1–5 related questions with stable ids, optional descriptions and choices, and optional free text. It uses Pi select/input dialogs in TUI and RPC, with a two-minute dialog timeout. It never uses confirm's ambiguous boolean or assumes a default: `answered`, `dismissed`, `cancelled`, and `unavailable` preserve actual partial answers and pending questions. Pending material decisions require asking in chat and waiting. Upstream visual decision boards, comp display and component-review pages remain in the playbooks; closing or losing UI does not authorize approval.

`impeccable_delegate` loads the whole adapted canonical role and resolves installed paths. Asset, document and manual-edit work use the configured `worker`; supplied-evidence finish review and read-only Assessment A use `reviewer`; browser Assessment A and detector/browser Assessment B use `worker`. Individual calls request foreground execution, `inherit_context:false`, and `isolated:false`, retaining extension/MCP tools. Role budgets stay at 24/30/30/12 turns (assessments 30). Agent's `max_turns` is a soft steering limit that permits grace turns. The adapter requests exactly N and synchronously cancels when foreground progress reaches N at `turn_end`, before another turn can execute tools. Public progress cannot distinguish a terminal answer from a continuation, so an answer on that boundary is conservatively retained as partial/cancelled; no extra turn rescues it. The adapter never supplies model or tier overrides, enables fleet types, installs global roles, or launches scripted workflows. Agent configuration stays authoritative; compatible configured soft limits at or below N are accepted without changing settings. Progress reporting incompatible isolation/background policies or an excessive soft limit triggers cancellation; final counts above the role ceiling are rejected. Agent validates the current fleet at dispatch; its startup prose list does not block a type enabled later. Returned failures and type substitutions are disclosed. Native `steered` within budget returns `wrapped-up`: the child terminated after soft-limit steering, and its actual output/artifacts need evidence assessment. Terminal errors, substitutions and policy conflicts return `partial`, preserving native details, artifacts and limitations without claiming completion or independent verification. Every executed terminal result sets `childTerminated:true`, `inlineSubstitutionAllowed:false` and `evidenceAssessmentRequired:true`; inspect output/artifacts and explicitly bound any remaining-work handoff instead of replaying the full role inline. Caller cancellation, user stop, role-boundary cancellation and native hard-limit abort retain distinct reasons. Unknown native statuses remain unresolved. Each critique assessment gets a separate packet without sibling results. Use distinct output paths for parallel writers and await them before verification.

A configured background override returns `active` with the actual child ID and a management handoff. Caller cancellation cannot stop a detached child. Retrieve its terminal result through `get_subagent_result` or stop/manage it through `/agents`; do not substitute inline work, duplicate the task, or start dependent work while it remains active. A child independently stopped through `/agents` returns `cancelled` even when the caller signal remains live; retain its actual partial output and stop the task without inline substitution. Nested child-safe Agent is detected from tool metadata and returns a complete main-session handoff before dispatch because it has no progress or structured outcome contract, including for configured background writers. Return this packet to the main session instead of executing the same nested Agent. A recognized pre-spawn unknown/disabled-type refusal for the requested type, with undefined details and no progress, returns `unavailable` with the actual message and upstream `fallbackPath`, permitting disclosed inline substitution where the playbook allows. Other unexpected text-only outcomes or exceptions after dispatch return `unresolved`, including failed boundary cancellation without established termination, preserving output and prohibiting duplicate/inline work until termination is established.

Finish-reviewer continuations return a handoff without dispatch because Agent resumes do not forward progress updates. Before a separately managed main-session continuation, inspect effective policies and actual partial evidence; a positive `max_turns` is still only a soft limit. Prefer a fresh finish review with the complete recaptures and prior fixes, or disclose the degraded review.

On Pi versions without callable `ctx.executeTool('Agent', ...)`, the tool returns the complete main-session Agent handoff. If no child was dispatched because no Agent/type is available, follow the named upstream degraded fallback and disclose the limitation; inline review is never labeled independent. The current runtime is verified on SDK 1.4; compatibility with peers >=1.3 uses API detection and handoff, without raising the minimum version.

## Vendoring and upgrade procedure

The explicit `tests/e2e/live-engine.test.ts` smoke uses a tracked disposable HTML project, a separate existing HTTP app server, actual native helper/boot and CLI polling, and protocol-faithful authenticated `/events` injections as test inputs. It checks real publication ack (`ok`, `id`, `status`, `file`), stops/restarts the owner and restores canonical pending work without Go, publishes/accepts through both the owner and registered Pi/faux tool bridge, inspects native journal/status, and asserts owned helper termination and app-server survival. It independently hashes the official pinned engine in an isolated cache with no ambient credentials. Offline executable fixtures cover remaining event shapes and failures; neither suite claims browser interaction or full AC-12 evidence.

The pinned source of truth is `upstream.json`. To re-import or upgrade:

1. Fetch the upstream tag/commit read-only into temporary storage, e.g.
   `git clone --filter=blob:none --no-checkout https://github.com/pbakaus/impeccable.git /tmp/impeccable && cd /tmp/impeccable && git fetch --depth 1 origin <commit> && git checkout <commit>`.
2. Copy the exact upstream paths listed in `upstream.json` into `vendor/impeccable-4.8.0/` (or a new `vendor/impeccable-<version>/` directory) and regenerate `vendor/.../MANIFEST.sha256` (sorted `sha256` of every file).
3. Point `upstream.json` at the new tag/commit/engine version, update the pinned `ENGINE_VERSION` in `src/resources.ts` and the checksums in `skills/impeccable/scripts/engine-checksums.txt`, and record any change in `LOCAL-PATCHES.md`.
4. Run `node extensions/impeccable/scripts/transform.mjs` and confirm it reproduces `skills/` and `prompts/` (the contract suite asserts this determinism).
5. Run `npm run test:impeccable` and `npm run typecheck`.

The engine binary itself is never committed: it is downloaded at runtime by `impeccable_run` (or the vendored launcher fallback) and verified against `skills/impeccable/scripts/engine-checksums.txt`.

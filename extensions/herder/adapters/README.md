# Herder for Pi

Herder is a native Pi extension package with package-owned planning skills.

## Install

See the [canonical installation and quickstart](../README.md#install) in the package README. For an adapter-specific profile example:

```text
pi --model <provider>/gpt-5.6-luna --thinking max
/herder-fire herder-plans --profile poorman
```

User-facing commands, planning behavior, run control, and lifecycle summaries are authoritative in the package README's [canonical planning and execution command reference](../README.md#planning-and-execution-commands). This document continues with the detailed Pi adapter and runtime contract.

### Active-Fire plan editing

The package README's [canonical planning and execution command reference](../README.md#planning-and-execution-commands) summarizes this user-facing contract; this section owns its reservation and revision-barrier mechanics. During an active Fire run, the adapter refuses mutating plan-configuration operations (`/herder-plans init`, `track`, and `untrack`) for the current session. `/herder-grill --plan <id>` is accepted only after the manager proves the target has no runtime, action, attempt, worktree, or approval evidence. The reservation withholds only that plan from scheduling, so unrelated work continues. After the confirmed target-local edit, the adapter raises a revision barrier: it stops new dispatches, waits for existing workers to settle, adopts the validated target-only change as the next immutable graph generation, and resumes scheduling automatically. Cancelling without changes releases the reservation. Explicit `--split` is rejected before reservation because active-Fire edit authority is target-local; finish or stop Fire before running the split standalone. `/herder-rework <plan-id>` is the started-plan counterpart: it reserves a blocked or exhausted non-integrated plan and injects Grill before any deletion. On model-requested finish, the adapter prepares the rewrite, presents the destructive host confirmation, records approval, settles only the target's workers, and then resets that plan's exact worktree, branch, and transient refs before recreating it from the current integration HEAD at round 1. Declining confirmation or cancelling Grill restores the pre-interview graph and leaves existing execution untouched; validation failure stops before worker settlement. Integrated plans and plans with active or integrated downstream consumers are refused.

### Planning-tool inspection responses

The native `herder_plan` tool presents `validate` and `shape` as compact summaries: graph identity, shape readiness, all context/plan issues and warnings, unordered overlap paths, and an ordered-overlap count. Validate also retains lifecycle/readiness counts and dependency waves. A successful parse or `shapeReady` never claims semantic readiness. Snapshot presents its input/hash provenance followed by the exact compiled Markdown once, without repeating local/shared source, index, or derived contract objects.

For these three read-only operations, `view: "full"` explicitly exposes the original JSON result, including derived contracts. Either view pages at 12,000 UTF-16 characters or 1,900 lines, below Pi's 50KB/2000-line limit including the continuation footer. Continue with the same operation/directory/plan/view, `offset: nextOffset`, and the returned `responseSha256`; collect all pages before assessing completeness. Continuation re-reads the source and rejects a changed presentation, requiring a restart at offset 0 without the old hash. It creates no temporary files, caches, or persistent configuration. These arguments are rejected on other operations before dispatch, so requesting another page cannot repeat a mutation.

Only model-facing content changes. Raw application results remain in tool `details.result`; CLI notifications, manager reply hooks, graph/snapshot hashing, and immutable assignment Markdown are unchanged. Full view is an inspection option, not a new source of plan authority.

## Responsibility boundary

The shared deterministic Run Manager retains ownership of plan state, SQLite accounting, stable branches/worktrees, immutable assignments, review rounds, recovery, verification execution, and serialized integration. The native Pi adapter supplies fresh child sessions and their lifecycle events, and delegates final verification selection—not execution—to the main Pi session.

Implementation ownership follows that boundary:
- `src/client/index.ts` owns transport recovery with stable operation IDs; the adapter does not retry manager work independently. A durable failed operation is an outcome, not a connection failure.
- `adapters/index.ts` owns run ownership, worker dispatch/terminal transport, and command/tool registration. `main-session-requests.ts` owns main-session request bindings, delivery deduplication, attention handoffs, and recovery follow-ups; its caches never replace durable manager authority.
- `worker-engine.ts` shares clean-session admission between roots and children, while root and nested execution retain their different cancellation and worktree-ownership rules.
- The Reviewer contract owns authority, frozen proof, setup, and the terminal envelope; the review protocol owns the review method. Both are mandatory root inputs. Nested reviewers retain standalone instructions because they do not inherit the parent's conversation.

Plan V2 is a breaking seven-section Markdown contract with authoritative A/V/T tables; old format is not accepted or migrated. See [Plan V2](../README.md#plan-v2-breaking-markdown-contract). The derived PlanContract is inspectable, but immutable compiled planText remains authority. Parser/shape validation runs no setup or check commands and cannot prove semantic sufficiency or eager dependency availability. Producers/Validate verify evidence and resolve uncertainty before authoring; Implementers perform declared bounded setup, canonical pre-edit T probes, and baseline diagnosis, then development/acceptance checks; Reviewers/Judges reuse prepared state and may repeat only repository-declared source-preserving restoration before independent checks. `SETUP` remains separate from `CHECKS`. Final checks belong to the separate main-session-selected manager manifest. **There is no automatic manager per-plan gate execution or new preflight worker.** Agent reports are not authoritative final verification. Suggested implementation routes do not override binding A criteria or scope: an equivalent bounded fix is acceptable.

Three generic package agents are available for every profile:

```text
herder.plan-implementer
herder.plan-reviewer
herder.plan-judge
```

Round-3 rescue specializes `herder.plan-implementer` in fresh context with unchanged tools, using the profile's optional `rescue` binding or otherwise its normal Implementer binding; it adds no worker role. SQLite schema version **19** supports fresh runs only: older databases are retained and refused, never migrated or deleted by schema handling.

The profile supplies each exact model and Pi thinking level at launch. Before repository mutation, Herder validates the root model, requested child-model efforts, and package-owned definitions against the same Pi model runtime used for children. It never substitutes another model after failure.

## Orchestration workflow

Pi is Herder's only host. The adapter translates deterministic manager actions into native clean child sessions; it does not schedule work itself.

### Service and dashboard

Fire, resume, revise, worker events, edits, stop, verification, and reignite acks use durable SQLite operations. A POST only validates and accepts an idempotent operation ID; clients poll short reads for its result. Reconciliation, Git integration, and verification run serially on the manager worker without holding an HTTP request, while `/health`, `/v1/status`, operation submission, and operation polling remain responsive. The latest manager reply is persisted as a snapshot, so status never queues behind heavy work. A healthy authenticated service is reused; a live but unresponsive one is waited out through a grace period and replaced only when wedged, never duplicated. Accepted operations, snapshots, and run authority survive service replacement. When Orca-owned environment markers are present, Herder asks the Orca CLI to open the loopback dashboard in the current workspace browser; it does not attempt editor-specific forwarding elsewhere. In non-Orca terminals, the adapter reports the loopback dashboard URL without host-specific forwarding. README lifecycle is a projection; Pi session entries are UI hints only.

### Worker transport

The manager returns a batch of exact actions. For each action, the adapter creates one native Pi SDK session with:

- the exact profile-selected role agent, model, thinking level, and service tier;
- a new persisted `SessionManager` with no parent and zero inherited messages;
- the manager-owned stable worktree as `cwd`;
- the complete manager prompt and immutable assignment evidence; and
- Pi's built-in `grep` and `find` tools, plus Ponytail's exact `pi-extension/index.js` from Pi's trusted user Git store only for Implementers, with no ambient/project discovery or extension skills, prompts, or themes;
- no managed temporary worktree or second scheduler; and
- scoped parallel `Agent` and `get_subagent_result` tools for bounded foreground or background delegation.

The adapter prepares the clean sessions, returns action IDs and opaque `pi-worker:` session handles as one dispatch-results event, and starts workers only after that event is accepted. At that boundary it appends a bounded, expandable blue input card to the root Pi transcript; when the child settles, it appends a bounded, expandable green output card, or a red interrupted-output card, carrying the plan, exact model, thinking level, service tier, response, duration, and token evidence before reporting the terminal event. Each completion maps directly to its action and returns token and timing evidence as one terminal event. Event operations reuse the same event and operation identities across retries; a serialized adapter queue prevents simultaneous completions from racing manager transitions. The manager applies review policy, accounting, integration, and role-agnostic slot backfill before publishing the next snapshot. Worker sessions never receive the root transcript, and transcript cards are excluded from model context.

### Scoped nested delegation

Herder owns a bounded nested executor, independent of the standalone `extensions/subagents` scheduler and telemetry bus. Each root role has hard runtime caps of four direct children concurrently and eight launches per action, unchanged by prompt policy child counts. Multiple `Agent` calls in one model response execute in parallel; `run_in_background: true` returns an ID while the caller continues.

The package-owned types are `recon`, `searcher`, `worker`, and `reviewer`:

- **Recon** is a strictly read-only source navigator with worktree-scoped read/grep/find/ls overrides and no extensions. Initial capability triage returns `HANDOFF_REQUIRED` immediately for runtime, implementation, or general-review objectives. Supported questions return `ANSWERED` or early `PARTIAL` when static sources are exhausted or a tool mismatch emerges, with `ANSWER`, `EVIDENCE`, and `REMAINING`. A useful early handoff is success. Recon has a fixed hard one-hour wall-clock deadline including setup, compaction, and retries. Expiry requests session cancellation and returns `timed_out` with any available partial output after at most a five-second cleanup grace; partial output is incomplete evidence. The caller owns continuation, with no automatic unchanged relaunch.
- **Searcher** is a strictly read-only leaf, primarily remote web research with built-in grep/find only for explicitly delegated local evidence. It loads only `npm:pi-web-access`.
- **Worker** may mutate and is available only to Implementer. It additionally loads Ponytail's exact trusted user-Git `pi-extension/index.js`, which adds instructions but no LLM tools. It reuses parent-prepared dependencies and may run repository-declared setup only with explicit sole ownership delegated by the parent; sibling/parent installs never compete. Cancellation retains ownership until its setup, prompt, and cleanup settle; the bounded scout cleanup policy never releases a still-mutating worker's worktree.
- **Reviewer** is available only under root plan-reviewer. It inherits that parent's exact model, thinking level, and service tier; loads no extensions; and has exactly read, bash, grep, find, ls, Agent, and get_subagent_result. Its unrestricted bash makes `readOnly: false` honest: source preservation is a behavioral contract, not a sandbox. The root Reviewer owns shared preparation before child checks. A nested Reviewer normally consumes that state; only an explicit sole-setup delegation permits repository-declared locked/pinned restoration, still without tracked manifest/lock/source edits or competing installs. Targeted safe reproductions use external scratch for other writes and avoid source/plan edits or mutation of the shared frozen worktree. Each reviewer may optionally launch only recon leaves, at most one concurrently and two total per subreview. Cancellation waits for the reviewer's Bash-capable session to settle before releasing the worktree; its recon leaf still has bounded cancellation. There is no general recursive agent.

Root Reviewer and Judge retain direct recon/searcher access; Implementer also retains worker access. Recon keeps the package-owned scout binding `gpt-5.6-luna` at `max` on the fast tier. Searcher uses the profile's optional `searcher` binding, otherwise the same scout binding; worker inherits its parent action binding. In `universe`, Searcher uses Sol xhigh, leaving Luna only for Recon. Optional rescue/searcher bindings are hashed with the profile, saved in the existing immutable SQLite binding, and restored on restart rather than reselected from the live catalog. All leaves lack Agent/result tools and cannot recurse. Every child shares the stable manager-owned worktree and cancellation lifetime and receives a clean direct Pi SDK session with a private session-storage directory. Recon uses scoped SDK-compatible tool overrides; other children retain Pi's built-in local tools. Searcher loads only the explicitly installed, allowlisted `npm:pi-web-access`; worker loads only Ponytail; recon and reviewer load no extensions. Children have no inherited conversation, extension skills, prompt templates, themes, project context files, scheduling, resume, or secondary worktree. Only reviewer receives scoped Agent/result tools for its recon leaves. Extension discovery stays disabled; exact trusted user package paths are required, project-scoped shadowing is rejected, and missing packages fail with an explicit `pi install` instruction.

Recon's tool boundary applies to direct children and reviewer grandchildren. Paths must remain inside the assigned worktree; `.git`, `.herder`, and symlink traversal below that root are rejected, including recursive searches. Recursive searches also skip `node_modules`, while source JSONL fixtures remain available. Recon disables all ignore-file and ripgrep-config processing because even `--no-follow` can read symlinked ignore files; ignored build outputs may therefore appear, so callers should give narrow source paths/globs. Find uses Node glob semantics: name hidden path components explicitly (for example `.github/*`). Search uses installed `rg` from host PATH or Pi's bin directory, with no automatic download; missing tooling, cancellation, or output overflow is an explicit incomplete-evidence error. Parent roles supply necessary historical diffs and external evidence inline in the task, not as outside paths or directory grants. Denials request a `PARTIAL` handoff, not transcript archaeology or an unchanged retry. These are tool-level source-navigation restrictions, not an OS sandbox against hostile concurrent filesystem mutation; other roles' permissions are unchanged.

Roles prefer Recon for bounded unfamiliar-code navigation and static caller/data-flow traces, supplying a concrete question, starting paths, stopping boundary, and compact evidence request. They reuse the returned map, retain implementation/runtime proof/review judgment, and skip delegation for known-path reads. This aims to reduce repeated exploration; no live speed or quality improvement is claimed without a benchmark.

Collect every background direct result before the caller returns, including terminal timeout/error results. `get_subagent_result` accepts `wait_any: true` for the first uncollected background direct result or `agent_id` for a specific child, mutually exclusively; omitting both lists direct children. Waiting defaults to true for either selector. Each wait is bounded to 60 seconds and then returns running without cancelling the child. When idle, wait again rather than short-polling or issuing a parallel all-results barrier. Collection is caller-driven, not an automatic LLM push notification. Uncollected children fail the action closed; reviewer uncollected grandchildren also fail closed. Stops and parent completion cascade abort/settlement through the tree.

The live TUI tree is ephemeral and includes both reviewer and recon levels. Grandchildren use compact inline activity, tool-count, token, and elapsed-time rows, omitting repeated model/thinking/tier and context statistics; failed scouts remain visible after their reviewer completes. It is not persisted to manager SQLite or exposed on the dashboard; parent completion removes it after settlement. Terminal usage counts every descendant exactly once, keeping parent-session tokens on the parent model and a breakdown by nested type/model; the dashboard implementation card shows that breakdown. Parent and nested extension sessions bind noninteractively before prompting and emit `session_shutdown` before disposal.

### Three-round plan closure

Each plan has at most three substantive rounds. This progression covers ordinary code failures; explicit ENVIRONMENT/INVOCATION blockers instead enter same-round operator attention without automatic code repair/retry:

1. **Quick path:** Implementer, then independent Reviewer. Evidence-complete blockers may authorize round-2 guided repair directly.
2. **Adjudicated repair:** Implementer, then independent Reviewer. Approval skips Judge; only nonapproval invokes Judge. `DONE` requires original criteria and required gates to pass. `REPAIR` authorizes the sole third round on the ordinary review-driven path; unresolved authority or no safe bounded path remains attention, not invented scope.
3. **Rescue:** the existing Implementer in a fresh context with unchanged tools and delegation limits, using the optional rescue binding or otherwise its normal Implementer binding, then independent Reviewer. There is no round-3 Judge or fourth automatic mutation.

The manager may also advance round 2 to `RESCUE` for manager-proven operational failures or conflicts without any prior Reviewer or Judge (`PASS_DOCUMENT: none`); use the unchanged original assignment and precise manager-supplied failure evidence, never an invented waiver.

Judge's terminal envelope includes `PASS_DOCUMENT`: a self-contained acceptance document of at most 16384 characters, required for `REPAIR` and `none` otherwise. It specifies remaining authorized finding IDs, concrete acceptance conditions/checks and required evidence, rejected findings with reasons, scope invariants, and unresolved decisions. Its content uses prose/bullets, not unindented uppercase field labels that could be parsed as new envelope fields. It cannot weaken the original criteria or add scope. The runtime persists it in the immutable terminal action result and delivers the document with its actionId/hash; there is no separate pass-document file.

The rescuer receives the unchanged original assignment, the binding round-2 Judge document for ordinary review-driven rescue (or precise failure evidence for operational rescue without one), and prior attempts/findings/check evidence. It may change implementation approach within the authorized scope but cannot rewrite the acceptance document or self-approve. Third review is contract-focused plus serious introduced P0/P1 regressions, not broad rediscovery; if no evidence-complete discovery has occurred, it must perform that first required discovery using the same Plan V2 risk rule, regardless of round. Unresolved exhaustion becomes a durable request in the existing serialized main-session attention queue, not a new role or repair loop.

### Reviewer protocol

Every root Reviewer receives `assets/review/code-review-protocol.md` alongside its role contract. The parent verifies the compiled assignment/hash and frozen authority, then sends self-contained relevant packets; children never need coordinator checkout or source-plan authority.

Plan `DISCOVERY` uses the existing Plan V2 Risk floor: **LOW = 1, MED = 2, HIGH = 4** fresh `reviewer` children; missing risk defaults conservatively to HIGH. Escalate for actual diff risk, including authorization/authentication, persistence, concurrency, public boundaries, and executable Markdown/prompt policies. Never downgrade merely for diff/file size or documentation extension. Record the effective risk and count rationale. First discovery in a later round uses this same rule. `FINAL_AUDIT` retains four parallel reviewers and full aggregate coverage for now. These are prompt policy counts, not changes to the eight-call/four-concurrent hard runtime caps or model bindings.

Every changed hunk and named cross-boundary question has explicit ownership. Plan/rules/scope, diff correctness, contextual regression, and tests/trust boundaries remain four coverage lenses regardless of child count, not redundant whole audits. Each child may run targeted safe bash reproductions and use bounded recon navigation; the parent runs required shared gates once. `VERIFICATION` defaults to one scoped child for accepted open IDs and repair-delta regressions; scale only for distinct risky repair boundaries up to four, with explicit partitions. Do not reopen broad discovery after it is complete, or resolved/rejected findings without new evidence. Preserve IDs; a missing finding from a partial report is not resolution. Round-3 review follows the Judge pass document when supplied, or precise operational failure evidence without one, against unchanged original criteria as described above.

Materiality comes before expensive proof: a candidate needs a concrete plausible trigger and material consequence, or an explicit failed acceptance/scope obligation. Do not actively seek optional P2/P3 improvements. Zero findings is valid; never suppress confirmed serious defects to meet a count. Children separately label mandatory coverage gaps (`COVERAGE_GAP`) and credible material concerns (`MATERIAL_CONCERN`) in `UNRESOLVED`. Reject unsupported speculation with concise reasons, without demanding every hypothetical be proved false. Missing proof alone neither rejects a credible concern nor promotes it to a blocker; child confidence scores are not an admission gate. The parent independently checks materiality, verifies surviving blockers, reconciles coverage, and retains unchanged evidence, severity, relationship, repair rules, and exact terminal envelope. Serious unresolved concerns or missing required checks/coverage remain incomplete, never approval. Targeted second opinions are optional, not a mandatory skeptic or second discovery wave. Root recon/searcher remain evidence helpers, never substitutes for actual reviewers or parent verification.

`HERDER_REVIEW_TIMEOUT_MS` accepts a positive integer no greater than 2147483647; unset disables it pending calibration. It is one wall-clock deadline from root Reviewer start per action, including SDK compaction, SDK retries, and every descendant—not a fresh budget per child or SDK retry. Exhaustion cancels the review tree and enters same-round `operator_attention`, with no automatic retry or approval. Only an explicit operator retry starts a fresh action budget after exhaustion. Safe Bash-capable settlement may exceed the deadline before worktree ownership is released. A child timeout alone is neither a defect nor approval: complete mandatory work within the remaining root budget or return `BLOCK` when genuinely unable. See [review calibration](../TESTING.md#bounded-review-policy-and-calibration); no live speed/quality gain is claimed yet.

### Final verification and bounded recovery

Herder does not scrape shell commands from plan prose. When all ordinary plans are integrated, the manager persists an exact-tree verification request and pauses. The adapter injects that request into the current main Pi conversation. The main model inspects the frozen integration worktree, repository scripts/manifests, pyproject/uv or Nix declarations/locks where applicable, CI/instructions, and compiled A/V/T evidence. It selects the smallest adequate non-redundant manifest of direct argv commands through the canonical declared environment, each with a TreeRelative working directory and rationale, then calls `herder_verification`. It does not translate V command strings mechanically. Distinguish setup prerequisites from checks: no ad hoc global/unpinned installs, opportunistic uvx/npx downloads, credential injection, or ambient HOME workarounds. When a declared pinned asset must be created under the isolated gate HOME/cache, select the repository's canonical setup-and-check script as one gate so preparation and its check share that private environment; keep their log evidence distinct. Do not invent a shell chain, assume Playwright, or use a prep-only gate to seed a later fresh gate. The tool returns immediately after durable submission. The manager validates every binding and path, executes the commands asynchronously, stores log hashes and results, and only then proposes the final aggregate Reviewer. If no main session is available, the request remains durably paused and is re-exposed on resume.

If an authoritative gate fails, the adapter injects a structured recovery turn containing the exact log path, failed gate, frozen head/tree, and a request-bound capability. Every failed verification request is one immutable classification episode, and the prompt displays that episode's request/hash, head/tree, and canonical gate evidence. The main session submits exactly one classification for the current episode: `manifest_error` corrects wrong argv/manager/cwd by replacing the manifest; `transient` performs one unchanged retry; `code_defect` opens a writable integration-repair transaction only for a demonstrated source defect; `environment` records proven prerequisite absence as a request-bound non-mutating decision outcome, alongside design, scope, credential, or product ambiguity. Environment classification authorizes no source edits and consumes no code round. Missing tools/setup are not guessed code repairs; report exact manager/command/cwd/error and prerequisite. Inspect canonical uv/Nix/package-script invocation and source evidence before deciding. A newly failed successor closes the prior episode and is classified from its own evidence; history remains queryable and the prior classification is never rewritten. Only after a successful `code_defect` repair `begin` may the owning session edit failure-related paths in the assigned integration worktree; local diagnostics are optional and non-authoritative. For a code defect, the owning session stages and creates the next bounded repair commit or amends the logical repair commit while retaining the fixed parent, confirms a clean worktree, and submits its observed `HEAD`; Herder only validates the clean single-parent commit and reruns the inherited authoritative gates. `finish` and `cancel` are request-bound, replay-safe transitions. Accepted code commits remain capped at three across episodes, manifest corrections do not consume code rounds, and an unchanged transient retry cannot reset when the head/tree/gate program is identical. Retained gates stay in their exact order, and additions must be explicit. `/herder-resume` remains operator recovery for interrupted or deliberately deferred state; ordinary deterministic integration defects no longer require graph revision. The frozen tree is otherwise never edited in place.

### Reignite write

An `environment` decision is available only after the canonical gate (including any repository-owned in-gate setup) actually failed or lacked authority. It stays paused until the operator resolves the verified external prerequisite and explicitly invokes `/herder-resume`. Resume validates the recorded request, graph/profile, clean frozen head/tree, and begin-ref namespace; it atomically records one successor request/manifest with the **same ordered canonical gates**. It grants no source edit authority, credential/HOME inheritance, code round, or transient-budget charge. Restart/replay uses that same successor. A failed successor opens a fresh unclassified episode without another automatic retry; environment-only preparation does not require a corrective plan or `revise`.

Cancelling final RUN attention, including REQUIREMENT decisions, preserves the frozen tree and leaves the run paused. `/herder-resume` preserves that cancellation rather than approving, completing, or silently restarting the audit.

After exact-tree gates pass, a completed, parseable final Reviewer report without a classified blocker completes the original run. ENVIRONMENT/INVOCATION retains same-round operator attention; REQUIREMENT retains confirmed recovery/decision authority rather than claiming completed review. Only eligible residual material blockers—P0/P1 `BLOCKING` findings with `PLAN_REQUIREMENT` or `PATCH_REGRESSION` relationship—are recorded as an executable pending dossier. Advisories remain in reports, not executable scope; advisory-only reports do not trigger automatic Reignite drafting. For eligible blockers, the adapter injects one `HERDER_MAIN_SESSION_REIGNITE_V1` follow-up while this session owns the source run, naming a previously unused repo-root sibling (`herder-reignite`, then `herder-reignite-2`, …). The main session writes only there with `herder_plan` `init`/`shape`/`validate`, then calls `herder_reignite` with the `graphSha256` returned by `validate`. `planDirectory` may be the source run or the allocated sibling; acknowledgement always targets the source run. Fire of the allocated directory is a separate user command. A failed or ignored write leaves the source run complete; `/herder-resume` on the source directory re-injects the same request and path. Attach still refuses `complete`.

### Path kinds

Herder distinguishes host locations from positions inside a known tree:

- **LocationRoot** — absolute realpath host locations such as `repositoryRoot`, `planDirectory`, plan/integration worktrees under `<planDirectory>/.herder/worktrees/`, and assignment/log paths.
- **TreeRelative** — positions inside an already-known LocationRoot. Verification gate `cwd` is TreeRelative only (`"."` or a clean relative path such as `pkg`). Absolute gate `cwd` values are rejected with no compatibility rewrite; execution resolves `path.resolve(integrationWorktree, gate.cwd)`.

### Attention, concurrency, and recovery

Blocked worker envelopes retain their existing fields with one optional fact: `BLOCKER_KIND: ENVIRONMENT | INVOCATION | REQUIREMENT`. Implementer STOPPED/FAILED, Reviewer BLOCK, and Judge NEEDS_INPUT/BLOCKED may report it. Success and ordinary code-defect outcomes omit it. Contradictory success/blocker values, invalid values, or ENVIRONMENT/INVOCATION combined with defect findings/failed scope are rejected; classification grants no approval, mutation, or waived checks. Review/Judge frozen-tree integrity checks precede blocker handling.

ENVIRONMENT identifies prerequisites still missing after permitted repository-declared setup failed or setup authority was absent; INVOCATION identifies wrong manager/argv/cwd. Both route to durable `operator_attention` with cause `verification_environment`, preserving the recorded role/ready phase and **same substantive round**, with no automatic retry or guessed code repair. Report setup and check evidence separately with exact manager/command/cwd/result or error and the prerequisite/correction. Only explicit request-bound retry/cancel continues the blocked work; unrelated plans continue. Preserve dirty blocked implementation worktrees; never accept unreviewed changes. REQUIREMENT follows existing confirmed `plan_recovery`/`user_decision` boundaries, not inferred permission to expand scope.

Three-round exhaustion reuses this durable serialized attention queue. The root receives a decision dossier containing implemented and remaining work, checks/results and gaps, prior attempts, recommendation, and frozen action/assignment/commit/tree identities. The request permits only these exhaustion outcomes:

- **Accept:** explicit user confirmation of clean, independently reviewed frozen changes, with gaps/waivers recorded against the exact request and evidence. Dirty, unreviewed, or in-progress-rebase surfaces cannot be accepted. Acceptance is not a claim that failed or unrun tests passed; normal integration trust checks still apply, and separate final-run verification remains mandatory.
- **Revise target:** a confirmed target-only replacement in a new immutable generation. Carry prior attempts, findings, and checks as history, not authority for the new assignment.
- **Stop:** preserve the branch and artifacts for user inspection or manual continuation.
- **Defer:** retain the unresolved durable request.

An exhausted generation cannot use unchanged retry to obtain a fourth automatic mutation. Unrelated plans continue; dependent plans wait for resolution and integration. These choices need neither a new attention queue nor a new role/profile.

The adapter holds a private exclusive ownership lock for each controlled run. A live foreign Pi PID blocks attach and dispatch; a safely parsed dead owner may be reaped, while malformed, symlink, or non-regular lock state fails closed. `maxParallel` is the complete Implementer/Reviewer/Judge pool. No control slot is reserved. Reviews and judgments for one plan may overlap implementation on another; only integration is serialized in the manager service. Substantive blocked transitions create `plan_recovery`; Judge questions create `user_decision`; exhausted provider or transport handling creates `operator_attention` and resumes the recorded role without plan rewriting. Final Reviewer residuals do not wait for `user_decision`. The adapter presents exactly one durable request in deterministic plan-ID order as a typed custom follow-up message when the main session settles, acknowledges only after injection succeeds, and re-exposes it after status refresh, `/herder-resume`, or replacement. Answers carry the request ID and decision; the adapter binds immutable request and recovery Git evidence. `plan_recovery` keeps the Grill one-question and final-confirmation guarantees; outside substantive exhaustion it permits a justified unchanged retry, distinct from a target-only validated replacement, and edits only the confirmed target plan. Defer leaves the request durable. After an unchanged retry, validated replacement, or rejection, the manager reschedules the recorded continuation. `/herder-resume` re-exposes unresolved requests after a reload. Unresolved attention blocks planning mutations but never reserves a worker slot or stops unrelated scheduling. Recovery cleanup force-removes only the exact manager-owned failed worktree and branch after identity checks; SQLite attempts, generations, approvals, findings, worker responses, usage, verification evidence, logs, and the completed recovery record remain intact. Before Pi reloads, switches, forks, or exits the current session, the adapter aborts and settles its in-process children without holding shutdown open for manager reconciliation or dispatching replacements from the stale session. The replacement or later resumed session reports each vanished handle interrupted so the manager applies its transport-retry policy; a foreign or legacy engine handle fails closed instead of dispatching a competing worker. Plan edits pause resume on graph drift; `/herder-revise` adopts a validated new immutable generation once workers settle. Stop aborts active child sessions, marks their exact actions interrupted, and preserves repository evidence.

## Final verification environment

Final verification already has **bounded npm-only locked preparation** in GitDriver: for direct npm/npm.cmd/npx/npx.cmd gates whose cwd has a package manifest declaring dependencies but no node_modules, it requires an npm lockfile and temporarily runs `npm ci --ignore-scripts --no-audit --no-fund`. It removes the node_modules it created after the gate (and on preparation failure), leaving pre-existing modules alone. This is not a universal preparer or permission to download an undeclared/unpinned npx package, prepare uv/Nix, or orchestrate arbitrary tools.

Pinned tool/browser assets use no new manifest field or shared host cache. If the repository declares a canonical setup-and-check script backed by its tracked manifest/lock/config, the final manifest may select that direct invocation as one gate. The script prepares the pinned asset and then runs its check under the same fresh isolated HOME/XDG cache, reporting setup output separately in the gate log; the private state is removed afterward. Because every gate receives a new state root, a setup-only gate cannot make an asset available to a later gate. If no canonical combined invocation exists, the asset remains an environment prerequisite rather than a guessed Playwright command or generic dependency workflow. Preparation is distinct from check success and can fail before check evidence exists; never claim an unrun check passed.

Final verification gates run with an explicit minimal environment. Command discovery (`PATH`), locale settings, and the Windows launch variables required to start ordinary commands are retained; ambient variables are not inherited. In particular, credential variables and ambient configuration are unavailable to deterministic gates.

Each gate receives a fresh private state root under the external verification log directory. `HOME`, XDG configuration/data/cache/state/runtime paths, platform home and application-data paths, and temporary directories point into that root. The root is removed after the gate evidence is finalized, while the mode-`0600` log and its hashes are preserved.

Child stdout and stderr are drained into one combined log with a fixed 16777216-byte child-output cap. On overflow, the runner appends `\n[herder] gate log truncated at 16777216 bytes\n` exactly once outside that cap and reports `logTruncated: true`; `logBytes` and `logSha256` describe the final on-disk bytes, including the marker. Under-limit single-stream bytes remain unchanged, but pipe capture may change undocumented cross-stream interleaving.

Durable gate results record `outcome` (`passed`, `command_failed`, `unavailable`, `timed_out`, or `runner_error`), optional `error`, `timedOut`, and `signal`, alongside exit/log/tree evidence. These describe process execution, not diagnosis. `unavailable` concerns launching the selected command; a uv/Nix wrapper that starts but cannot locate its nested tool may instead be `command_failed`. Neither exit 127 nor regex/log-text guesses prove a source defect. Inspect canonical manager invocation, declared prerequisites, and source evidence; choose `manifest_error` for a wrong invocation and non-mutating `environment` for proven prerequisite absence. Preserve exact-tree and minimal-environment guarantees rather than compensating with credential injection or ambient HOME.

Credential-backed verification is unsupported until it has a separate safe contract. Gate logs are not raw-log-redacted; artifact sanitization is a separate responsibility.

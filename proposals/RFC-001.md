# RFC-001: Run pika on both self-hosted servers and Cloudflare

| Field | Value |
| --- | --- |

| Status | Draft |
| Created | 2026-11-13 |
| Affects | `services/pika`, `services/pika/web`, `services/pika/docs/SPEC.md`, `services/pika/docs/NODE.md` |

## 1. Summary

This RFC proposes that `services/pika` be deployable in two ways from one codebase:

- **Server:** the existing native binary (axum, tokio, SQLite, local blob files).
- **Cloudflare:** a Worker with Durable Objects (DO, SQLite storage) and R2.

Both targets share a `pika-core` crate holding derivation, redaction, read, search, and relay logic. They implement the same SPEC and must pass the same end-to-end suite. To make that possible, raw trajectories move out of SQLite into an object store as sealed segments, storage access goes behind narrow interfaces, and object I/O is separated from SQL transactions.

## 2. Motivation

- **No server to operate.** A Cloudflare deployment needs no VPS, reverse proxy, TLS setup, or disk management. It comes with point-in-time recovery for DO storage.
- **A better fit for idle long-lived connections.** Relay and pika-node connections are mostly idle. Hibernatable WebSockets keep them open without billing for idle time.
- **Low cost at current load.** About $5–15/month (§9).
- **Self-hosting stays supported.** Users who do not want a third party holding their data, and development and tests, keep the native server.
- **Storage growth.** Raw lines in SQLite grow without bound (one machine adds about 3.8 GB of session files per month). The segment store (§5.2) fixes this on both targets.
- **Desktop client.** The planned desktop client is a thin client: it serves its own UI and talks to a server that holds the data. It must work against either target unchanged, so both must expose the same API.

## 3. Goals and non-goals

### Goals

- One SPEC and one `pika-core`, two deployment targets.
- The ingest protocol, read API, agent API, relay protocol, and nodes protocol stay wire-compatible. Existing clients (`extensions/pika`, `plugins/pika-relay`, `pika-node`) need no changes.
- Both targets pass the same `e2e.sh`.
- An existing server can be migrated to Cloudflare without data loss.

### Non-goals

- Multi-tenant hosting. Each deployment serves one owner.
- Feature differences between targets, except deployment-specific authentication (§6.5).
- Changing search semantics. CJK search must keep matching two-character words.

## 4. Background

### 4.1 Current architecture

- One Rust binary with one SQLite database (rusqlite, bundled). All writes go through a write lock in `store.rs`, and reads use a pool of up to 16 connections.
- `lines` keeps verbatim stream lines as the source of truth. Lines over 1 MiB go to the content-addressed zstd blob store `blobs/<h[0..2]>/<h[2..4]>/<h>.zst`.
- Derived tables (`sessions`, `entries`, `turns`, `model_calls`, `usage_events`, `tool_calls`, `herder_*`, `search_docs`) are rebuilt by `pika reindex`.
- Search is FTS5 (`search_fts`) with the custom tokenizer `pika_cjk` (`tokenizer.rs`), registered through C FFI. It indexes CJK runs as overlapping character pairs.
- Relay (`relay.rs`, 3,050 lines) and nodes (`nodes.rs`) run on tokio WebSockets and keep state in memory. Login rate limits are also kept in memory.
- `web/dist` is embedded with rust-embed.

### 4.2 Load

Public statistics, 2026-10-30 to 2026-11-12 (14 active days):

- 2,448 sessions and 108,915 LLM requests, which extrapolates to about 230k requests and 5.2k sessions per month.

Local session files on one machine, last 30 days:

- 1,505 files, 3.8 GB in total.
- Sizes: p50 0.40 MB, p90 2.77 MB, p99 44 MB, max 160 MB.
- A sampled 17.6 MB file compressed with zstd to 10 MB.

Not yet measured: the production database's `dbstat` breakdown, its blob directory size, and the ingest request rate.

### 4.3 Cloudflare constraints

Limits below are from memory unless linked. They must be verified in the spike (§8, phase 0).

| Constraint | Consequence |
| --- | --- |
| DO SQL is synchronous (`sql.exec`, `transactionSync`). There is no `BEGIN` and no `Transaction` object. | Transactions are closures. |
| R2 is async and cannot be awaited inside `transactionSync`. | Object I/O must happen outside transactions. |
| One DO is single-threaded. | Heavy reads block writes, so work is split across DOs. |
| About 10 GB of storage per DO. | Raw lines cannot live in DO SQLite. |
| Per-request CPU time limit. | Reindex and migrations run in batches driven by alarms. |
| No custom FTS5 tokenizers. | `pika_cjk` must be replaced. |
| wasm32, bundle size about 10 MB compressed. | No tokio runtime, no `std::fs`, and the C `zstd` crate needs care. |
| DOs are evicted from memory. | No in-memory state may be authoritative. |

## 5. Design

### 5.1 Crate layout

```
services/pika/
  crates/pika-core/     # no tokio, rusqlite, std::fs, or network
  crates/pika-server/   # native binary: axum, tokio, rusqlite, local files, CLI
  crates/pika-worker/   # workers-rs: Worker entry, DOs, R2, alarms
```

`pika-core` holds derivation, redaction, read queries, search query building, statistics, memory, relay and nodes state machines, auth logic, and HTTP handlers written against target-neutral request and response types. Each target supplies the interfaces in §5.3 and an HTTP adapter.

### 5.2 Segment store for raw trajectories

Streams are cut into size-based sealed segments. One object per session would force rewriting a whole object on every batch, and one object per line would mean millions of objects.

- **Tail.** The unsealed tail of a stream stays in SQLite (`lines`). Append, duplicate detection, 409 `conflict` and `gap`, and per-batch atomicity stay as they are, so the ingest protocol does not change.
- **Sealing.** A tail is sealed when it exceeds about 4 MiB or its stream has been idle for about 10 minutes (an alarm on Cloudflare, a timer on the server). Sealing has three steps:
  1. Write the verbatim bytes, zstd-compressed, to `streams/<key>/<start>-<end>.jsonl.zst`. `start` and `end` are the protocol's byte offsets.
  2. In one transaction, insert `segments(stream_id, start, end, object_key, size)` and delete the sealed tail rows.
  3. A crash between steps leaves at worst an orphan object, which a retry overwrites with identical bytes.
- **Lookup.** A line is found through `entries(sid, seq, offset)` plus a range lookup in `segments`. At p90 = 2.77 MB, most sessions have one segment.
- **Large lines.** Lines over 1 MiB stay separate content-addressed blobs, so one image does not bloat a segment.
- **Caching.** Sealed segments never change, so readers cache them by key: the Cache API on Cloudflare, an LRU in memory on the server.
- **Deletion.** Removes segment objects and tail rows. Blobs keep their reference checks.
- **Reads across many sessions.** Two reads that today scan raw lines in many sessions become derived data:
  - the `pi-extensions.command` aggregation (`read/extension_usage.rs`) gets a derived table filled at ingest;
  - the `instr(l.data, 'nestedCalls')` repair (`derive/mod.rs`) moves into reindex.
- **Request captures.** `requests` skeletons and `request_dict` stay in SQLite for now. Their size is measured in phase 0, and they move to objects only if they turn out large.

### 5.3 Storage interfaces

```rust
pub trait Sql {
    fn query<T>(&self, sql: &str, params: &[Value], row: impl FnMut(&Row) -> Result<T>) -> Result<Vec<T>>;
    fn execute(&self, sql: &str, params: &[Value]) -> Result<u64>;
}

pub trait Db {
    type Tx<'a>: Sql;
    fn read<R>(&self, f: impl FnOnce(&dyn Sql) -> Result<R>) -> Result<R>;
    fn write<R>(&self, f: impl FnOnce(&Self::Tx<'_>) -> Result<R>) -> Result<R>;
}

pub trait ObjectStore {
    async fn get(&self, key: &str, range: Option<Range<u64>>) -> Result<Option<Bytes>>;
    async fn put(&self, key: &str, bytes: Bytes) -> Result<()>;
    async fn delete(&self, keys: &[String]) -> Result<()>;
}
```

| Interface | Server | Cloudflare |
| --- | --- | --- |
| `Db` | rusqlite: a write lock plus a read pool | DO `ctx.storage.sql` and `transactionSync` |
| `ObjectStore` | Files under the data directory | R2 binding |

Signatures are illustrative and are settled in phase 1.

### 5.4 Separating object I/O from transactions

Every operation that touches both SQL and objects has three phases:

1. **Prefetch** (async): read the segments and blobs the operation needs, and check which incoming blobs already exist.
2. **Transaction** (sync): all SQL, with no I/O.
3. **After commit** (async): write sealed segments, delete unreferenced objects.

The server already orders blob writes this way: ingest writes a blob file before recording it, and deletion removes files after commit. The read paths that load blobs in the middle of a transaction must change. Both targets follow the same rule, so it is enforced in `pika-core` rather than per target.

### 5.5 Search

FTS5 stays on both targets. `pika_cjk` is replaced with application-side bigrams:

- At index time and at query time, `pika-core` rewrites each CJK run into space-separated overlapping pairs (`数据库连接` becomes `数据 据库 库连 连接`) and passes the result to `unicode61` with the current arguments. Matching semantics stay as they are.
- `snippet()` would highlight the rewritten text, so snippets are built in `pika-core` from the original text and the match positions.
- Changing the tokenizer needs a migration with a full FTS rebuild (§5.8).

Cloudflare AI Search was evaluated as a replacement and rejected:

- 500k files per hybrid instance, against about 700k entry documents per month.
- CJK requires `trigram`, so words shorter than 3 characters cannot match.
- At most 5 metadata fields.
- R2 sources sync every 15 minutes at best.
- Ingestion at $0.75 per million tokens, estimated at about $125/month for full entry text.

AI Search may later back a separate semantic "similar sessions" feature (one file per session with its user prompts and final answers), outside this RFC.

### 5.6 Cloudflare topology

| Component | Role |
| --- | --- |
| Worker | Routing, static assets (`web/dist` via Workers Static Assets), authentication checks, forwarding to DOs |
| `StoreDO` (one) | SQLite: tails, segment index, derived tables, FTS, auth, devices, memory. Ingest, read API, agent API, search. |
| `RelayDO` (one) | Relay sessions, rooms, mailboxes on hibernatable WebSockets |
| `NodesDO` (one) | Node presence and channel forwarding on hibernatable WebSockets |
| R2 bucket | Segments and blobs |

- Relay and nodes get their own DOs so that their message traffic does not queue behind ingest and statistics.
- Relay and nodes state lives in WebSocket attachments and DO SQLite. Pings use `setWebSocketAutoResponse` so heartbeats do not wake the DO.
- Background jobs (sealing, search rescrub, dream leases, expiring pairings and auth sessions) run on DO alarms. On the server they run as tokio tasks calling the same `pika-core` functions.
- The DOs get a location hint near the owner when first created.

If the single `StoreDO` turns out to be a bottleneck, statistics can be served from read-only aggregates refreshed by alarms. That is not planned up front.

### 5.7 Platform replacements

| Today | Change |
| --- | --- |
| `zstd` (C) | Try `zstd-sys` built for wasm32 in phase 0. Fall back to `ruzstd` on the worker (decode, weaker encode), with segments still readable on both targets. |
| `getrandom` | Enable its JS backend on wasm32. |
| `ureq` price fetch | An HTTP interface: `ureq` on the server, `fetch` on the worker. |
| In-memory rate limits | Persisted in SQLite on both targets. |
| Client IP from the socket peer or `X-Forwarded-For` | Also read `CF-Connecting-IP` on the worker. |
| `clap`, `rpassword`, CLI | `pika-server` only. Cloudflare management goes through the UI or a small admin API. |
| argon2 | Unchanged (pure Rust). CPU time per login is measured in phase 0. |

### 5.8 Migrations and reindex

- Schema migrations stay in `pika-core` and run on both targets.
- On Cloudflare, migrations that need a reindex or an FTS rebuild run in alarm batches with a cursor stored in `settings`, like today's `RESCRUB_AFTER`. Reads keep being served during the rebuild.
- A full reindex is billed per row written, so a migration that triggers one should be rare.

### 5.9 Authentication

Password login, sessions, devices, and pairing stay in `pika-core` and work on both targets. Per target:

- **Server:** unchanged. `password`, `proxy`, and `none` modes.
- **Cloudflare:** `password` mode works as is. The recommended setup is `proxy` mode behind Cloudflare Access:
  - verify `Cf-Access-Jwt-Assertion` against the team JWKS and check `aud`, instead of trusting the header blindly;
  - disable the `workers.dev` route so Access cannot be bypassed;
  - leave ingest, pair, relay, agent, health, and public paths open, as the existing Caddy and nginx configurations do.

Passkeys and re-authentication for pairing approval are worth doing but are left to a separate RFC.

### 5.10 Desktop client compatibility

The thin desktop client must work against either target:

- `GET /api/health` `version` and `features` become a compatibility contract. A deployment-specific difference is reported as a feature, never inferred from the target.
- Owner client tokens and CORS for the desktop origin are specified in `pika-core`, so both targets get them at once. Their design is left to a separate RFC.

## 6. Verification

- `cargo test` for `pika-core` and `pika-server`.
- The same `services/pika/scripts/e2e.sh` against `pika-server` and against `wrangler dev`, run in CI for both.
- Segment store property tests: for any sequence of batches, seal points, and crashes, reading a stream returns exactly the bytes ingested.
- Migration check: the old server and the Cloudflare deployment return identical `statistics` and `usage` for all time, and identical entries for a sample of sessions.

## 7. Migration from an existing server

No new protocol is needed:

1. Deploy the Worker and create device tokens.
2. Replay every stream, document, request, and blob from the old server into the new one through `POST /api/ingest/v1/batch`, reading streams with `export.rs`. Idempotency and 409/gap handling make the replay resumable.
3. Copy settings that are not in streams: publishing, hidden sessions, devices, memory notes. This needs a small export and import command.
4. Compare the results (§6), then point clients at the new URL.

Phase 1 helps the server even if the later phases stop, because it bounds the growth of `lines`.

## 9. Cost estimate (Cloudflare)

At current load, using prices from memory (verify before deciding):

| Item | Estimate per month | Cost |
| --- | --- | --- |
| Workers Paid base | — | $5 |
| Worker and DO requests | 0.3–0.6M | included |
| Worker CPU (20–50 ms per ingest) | 6–30M ms | $0–1 |
| DO rows written (50–200 per LLM request with indexes) | 12–50M | $0–a few |
| DO storage (derived tables and FTS only) | below 5 GB at first | included |
| R2 storage (segments and blobs) | tens of GB | $1–2 |

Total: about **$5–15/month**. The terminal traffic of `NodesDO` (20 WebSocket messages count as one request) is not estimated and is measured in phase 0.

## 10. Drawbacks and risks

- **Data custody.** Raw lines and captured provider requests are not redacted and contain secrets from agent context. A Cloudflare deployment hands them to a third party. Deployments that cannot accept this stay on the server target.
- **Two targets to maintain.** Every feature must work on both. Shared `pika-core` and the shared e2e suite are what keep them from drifting.
- **`StoreDO` capacity and throughput.** Derived tables and FTS must stay under the per-DO limit, and one thread serves all store traffic. Phase 0 measurements decide whether this holds for heavy users.
- **Reindex cost and duration** on Cloudflare (§5.8).
- **Large refactor.** 35 files use rusqlite today, and read paths that load blobs inside transactions must be restructured.
- **Platform lock-in** for Cloudflare users, limited by the fact that the server target and the migration path (§7) work in both directions.

## 11. Alternatives considered

- **Cloudflare only.** Rejected: it loses self-hosting and makes local development and tests depend on Cloudflare tooling.
- **A separate Worker implementation of the SPEC.** Rejected: two implementations of one SPEC drift apart.
- **Keep the server only.** Viable, but leaves operations work and unbounded `lines` growth. Phase 1 alone addresses the latter.
- **D1 instead of DO SQLite.** Not chosen: DOs also provide WebSockets, alarms, and single-writer semantics in one place, and D1 has a similar size limit.
- **AI Search for primary search.** Rejected (§5.5).
- **`trigram` tokenizer instead of application-side bigrams.** Rejected: two-character CJK words would stop matching.

## 12. Unresolved questions

1. Production `dbstat`, blob size, request-capture size, and ingest rate (phase 0).
2. Whether `contentless_delete` is available in DO SQLite, which would allow keeping `search_docs.text` in objects to shrink `StoreDO`.
3. zstd on wasm32: `zstd-sys` or `ruzstd`.
4. The router inside the worker: axum on workers-rs or a thin router in `pika-core`.
5. How Cloudflare deployments are managed without the CLI (tokens, password).
6. Seal thresholds (4 MiB and 10 minutes are starting points).
